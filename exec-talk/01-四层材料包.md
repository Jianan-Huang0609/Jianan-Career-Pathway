## 第 1 层 · CER 材料｜用真实业务证明执行力

### 1.1 先讲结论

CER AI Automation Tool 把高重复、高合规、强依赖专家的工作拆成可检查的流水线：**AI 做准备与 Draft，专家做 Review 与最终判断**。它覆盖四块能力，并已经进入真实 NMPA 递交流程。

### 1.2 历程与关键节点

```text
FY26 Q1                  2026.06                     V6                         下一步
PoC 验证        ───→     V2 迭代          ───→       Stage0–5 固定链路    ───→  泛化与平台化
验证真实痛点             从功能走向可复用            逐阶段留痕、可回验             Multi-BU / PDF / Chat / API
```

| 节点 | 做了什么 | 证明了什么 |
|---|---|---|
| PoC · FY26 Q1 | 从 CER 的重复劳动与专家判断边界切入 | 场景真实、问题可验证，不是为了 AI 找场景 |
| V2 · 2026.06 | 形成可比较、可复用的能力 | 从一次性试验走向产品化 |
| V6 · Stage0–5 | 固定顺序运行；CSV / JSON / DOCX 等中间产物可回看 | 自动化发生在可检查、可纠正的流程里 |
| 真实业务里程碑 | 3 份 CT CER 进入 NMPA 递交流程 | 项目进入真实合规业务，而非停留在 Demo |
| 下一步 | Multi-BU、PDF 多格式、Analysis Chat、能力 API 化 | 从 CER 产品走向组织可复用能力 |

> 技术材料对当前链路有更细的 `Stage00 + Stage0–5` 拆分；本次高管叙事沿用任务指定的 `Stage0–5` 口径，避免在 1v1 中陷入实现细节。

### 1.3 四块核心能力

| 业务动作 | AI 承担 | 人保留的权力 | 可展示证据 |
|---|---|---|---|
| 提取与填充 | 定位关键字段、结构化提取、自动填充 | 核对来源与最终确认 | 主 Deck、0618 PPTX |
| Comparison | 对齐两份 PTR、生成对比表、标出增删改 | 判断业务含义 | 主 Deck、Stage1 Casebook |
| Difference Analysis | 生成差异分析 Draft | 评估临床/安全影响并终审 | 主 Deck、3 分钟口播稿 |
| Literature Review | 批量解析、筛选、总结并生成报告 | 决定纳排与专业结论 | 主 Deck、全球分享演讲稿 |

### 1.4 数字不是装饰，是四类证据

| 证据类型 | 高管对话口径 | 它说明什么 | 来源 |
|---|---:|---|---|
| 效率 | 对比表：**2 天以上 → 约 5 分钟** | 把机械准备压缩到 Review-first | 本任务指定口径；career-portfolio 叙事与口播 |
| 效率 | 内容生成与文献综述：**天级 → 约 3 分钟** | 把专家时间还给判断 | 本任务指定口径；career-portfolio 叙事 |
| 来源守恒 | **Source Fidelity 100%** | 原文不被悄悄改写 | 0618 PPTX、全球分享演讲稿 |
| 风险底线 | **False Negative 0%** | 真实差异不漏 | 主 Deck、0618 PPTX、口播稿 |
| 可控代价 | **False Positive 约 12%** | 宁可多提示，由专家排除 | 主 Deck、全球分享演讲稿 |
| 对齐质量 | **列间对齐 >95%** | 比较链路具备可用稳定性 | 主 Deck、全球分享演讲稿 |
| 业务采用 | **3 份 CT CER** 进入 NMPA 递交流程 | 成果进入真实合规链路 | 本任务指定口径；career-portfolio 叙事与口播 |

> 内部 1v1 可以使用以上指标；如未来转为公开个人网站，必须重新做脱敏与发布审批。

### 1.5 三个方法论亮点

1. **业务驱动**：先有真实痛点、专家 know-how 和可回验输入输出，再决定 AI 做什么。
2. **边界感**：AI 只负责准备、Draft 与限定范围内的语义判断；缺证据不补写，专家拥有最终判断权。
3. **工程化落地**：把复杂工作拆成固定链路、质量 Gate 和可审计 artifact；失败也留下可定位证据。

### 1.6 下一步：从一个工具到共享能力

```text
纵向泛化                      横向复用                      交互升级
Multi-BU（XP / AT 等）   +    PDF / 多格式输入       +     Analysis Chat
        \____________________ Parsing / Comparison / Evaluation API 化 ____________________/
```

- **Multi-BU**：让不同 BU 在同一技术底座上替换业务规则，而不是从零重建。
- **PDF 多格式**：补足现实输入的格式差异与扫描件处理能力。
- **Analysis Chat**：必须建立在证据回指、受控范围与 Human Review 上，不做无边界问答。
- **API 化**：沉淀 Parsing、Comparison、Evaluation 等底层能力，供更多团队复用。

## 第 2 层 · AIDU Strategy（口述整理，名称待核实）｜把单点成果放进组织机制

> **重要说明**：以下全部为 Jianan 的 **AIDU Strategy（口述整理，名称待核实）**。`AIDU` 可能与 `AIDO / AIDI` 等同源，但在正式内部名称确认前，不把它写成已经核实的组织项目或制度。

### 2.1 五步机制图

```text
① 聚合所有 BU × 各 Function
                ↓
② 形成 AIDU Interface Team（口述整理，名称待核实）
                ↓
③ Interface 深入组织内部，挖掘 User Ideas
                ↓
④ 用评分机制筛选机会
                ↓
⑤ Fast Win 获得更多人才流入，继续放大
```

这套逻辑的重点，不是“多收集一些 AI idea”，而是形成一条可持续的组织回路：**发现真实问题 → 统一选择 → 匹配资源 → 快速验证 → 用结果吸引更多资源**。

### 2.2 两种落地模式 × 三类资源

| 落地模式 | 含义 | 适合场景 |
|---|---|---|
| 自提自落 | 提出 idea 的人或团队自己推动落地 | 有业务深度、能快速形成闭环的 Fast Win |
| 自提他落 | 由团队综合力量共同解决 | 价值明确，但需要跨职能技术或平台资源 |

| 资源来源 | 能提供什么 | 需要注意什么 |
|---|---|---|
| 公司内部人才库 | 懂业务、懂 AI、懂平台的组合 | 需要明确责任、投入与优先级 |
| IT 资源 | 平台、部署、数据与工程能力 | 需要把业务原型转成可维护产品 |
| 外部供应商的钱和资源 | 补充产能或专项能力 | 内部敏感资料、判断责任与知识沉淀不能外移 |

### 2.3 CER 的叙事位置

**建议说法**：

> “按我对 **AIDU Strategy（口述整理，名称待核实）** 的理解，CER 可以作为一个 Fast Win 候选样板：它来自真实业务痛点，由业务与技术共同落地，有量化结果，也开始进入真实流程。下一步我想验证的，是怎么把这个样板沉淀为其他 BU 能复用的能力。”

这句话刻意使用“**按我的理解**”“**候选样板**”，避免在名称与正式机制未核实前，代替组织下结论。

### 2.4 与高管校准的三个点

1. **名称与边界**：AIDU Strategy（口述整理，名称待核实）的正式名称、owner 与覆盖范围是什么？
2. **选择标准**：Fast Win 更看重业务价值、可复制性、合规可控，还是落地速度？
3. **人才机制**：Interface 成员如何进入、如何投入、如何评价成果？

### 3.2 角色成长线

```text
RA 业务深度
懂法规、流程、专家判断与风险边界
        ↓ 把隐性 know-how 结构化
AI 产品实践
定义问题、设计流程、做评估、推动真实采用
        ↓ 把项目能力沉淀为平台能力
AI Product
连接业务、技术、合规与组织资源，持续交付可复用价值
```

这不是“从 RA 转行去做技术”，而是：**把 RA 的业务判断力，升级为能定义和交付 AI 产品的复合能力。**

### 3.3 三个方法论标签

| 标签 | 我实际怎么做 | 高管能看到的潜力 |
|---|---|---|
| 业务驱动 | 从 CER 真痛点出发，用专家流程定义产品 | 能找到值得做的问题 |
| 边界感 | AI 做 Draft，专家终审；证据可回指 | 能在合规场景里负责任地创新 |
| 工程化落地 | 固定链路、分阶段评估、artifact 留痕 | 能把想法做成稳定、可复用的系统 |

### 3.4 3 分钟口播底稿

> 大家好，我是 SSME QT 的黄佳楠。今天想用几分钟，讲一讲我在 SSME 框架下做的这件事，以及它背后我的几个做事方法。
>
> 核心的一件事是 CER AI Automation Tool。CER 是医疗器械注册里的核心法规文档，过去它高重复、高合规，又高度依赖专家。我做的不是“让 AI 替代专家”，而是把流程拆开：AI 负责准备和 Draft，专家负责 Review 和最终判断。
>
> 具体做了四块能力：关键信息提取与自动填充、产品对比与高亮、差异分析、文献综述。从 PoC 到 V6，我搭了一条固定顺序、每一步都留痕可查的技术链路。每个环节都有 Evaluation 检查，专家随时可以回到原文核对。

>
> 这就是我在 SSME 做的核心工作，也代表我做事的方式。

## 第 4 层 · 潜在答疑｜把 1v1 变成方向校准

### 4.1 我想问高管的问题

| 方向 | 问题 | 为什么问这个 |
|---|---|---|
| QT 方向 | 作为老板，您最关注 QT 的哪几个指标？ | 对齐高管的价值尺度，避免只讲“做了很多”，却没有连接组织结果。 |
| QT 方向 | 您希望 QT 的 AI 自动化优先往哪里落地？是继续深化文档自动化，还是向更多业务链路扩展？ | 识别真正的战略优先级，也判断 CER 能否作为可复制样板。 |
| AI talent | 您怎么看组织内 AI talent 的发展前景？未来最稀缺的能力是什么？ | 用组织视角校准能力建设，而不是只凭个人兴趣下注。 |
| AI talent | 对我这样的年轻人，从 RA 走向 AI Product，您建议下一阶段重点承担什么？ | 把职业困惑变成可行动的责任选择，请高管给方向而不是泛泛鼓励。 |
| 组织机制 | 对跨 BU 的 Fast Win，您最看重什么：速度、价值、合规可控，还是可复制性？ | 帮助自己理解资源为何流向某些项目，也为下一次项目选择建立标准。 |
| 年轻人成长 | 回看您的成长经历，您觉得年轻人最容易低估、但应该尽早积累的能力是什么？ | 获得高管基于经验的长期建议，用开放问题收尾。 |

### 4.2 高管可能追问，我怎么答

| 可能追问 | 回答主线 | 证据锚点 |
|---|---|---|
| 为什么选 CER？ | 真实、重复、专家 know-how 丰富，并且输入输出可回验；不是为了用 AI 硬找场景。 | 四块能力、真实业务采用 |
| AI 会不会越界？ | AI 只做准备与 Draft；缺证据不猜；专家保留判断与终审。 | Source Fidelity 100%、FN 0%、Human Review |
| 怎么证明不是 Demo？ | 有效率和质量指标，也有 3 份 CT CER 进入 NMPA 递交流程。 | 时间压缩、质量底线、业务里程碑 |
| 你的独特贡献是什么？ | 把业务问题、产品定义、合规边界、评估与工程落地连接起来，并推动跨团队协作。 | 三个方法论标签、固定链路 |
| 下一步需要什么？ | 需要 Multi-BU 专家共创、PDF/平台工程资源，以及能力 API 化的协作场景。 | 下一步路线图 |
| 你想成为谁？ | 带着 RA 深度成长为 AI Product：能识别高价值问题，也能把它交付为受控、可复用的产品。 | 角色成长线 |

### 4.3 对话使用原则

```text
先给证据 → 再讲判断 → 最后提问
不把个人功劳盖过团队
不把尚未核实的组织名称讲成事实
不把 AI 能力讲成替代专家
不把内部材料直接用于公开传播
```
